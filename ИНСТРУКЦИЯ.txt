NoisyTCP (noisytcp) — инструкция
================================

Назначение
----------

noisytcp вызывает request_sock Reuse ABA Race CVE-2026-99288 в TCP-стеке
Linux и приводит к удалённому kernel panic. Это активный exploit-режим, а не
сканер и не проверка версии ядра.

Программа предназначена только для исследования собственных машин и
изолированных лабораторных стендов. Успешный запуск полностью останавливает
целевой Linux-хост и все его контейнеры. Пакеты отправляются с реального,
атрибутируемого адреса источника; программа не сканирует, не размножается,
не подделывает чужие адреса и не пытается уйти от обнаружения.

Реализован IPv4 request-queue-путь: режимы probe, verify, race и tw
(TIME_WAIT recycle для целей с tcp_syncookies=2). Режимы IPv6 и полного
child-socket ABA не реализованы.

Правовое предупреждение
-----------------------

Запускайте программу только на системах, которыми владеете, или на системах,
на тестирование которых у вас есть явное письменное разрешение. Падение
ядра затрагивает все процессы и контейнеры хоста, а также может привести к
потере данных.

Что реализовано
---------------

- probe/verify/race для IPv4 request-queue-пути;
- tw — переиспользование TIME_WAIT-сокета для целей с tcp_syncookies=2;
- автоматическая калибровка SYN-очереди бинарным поиском;
- детерминированная модель SYN-очереди (fill/drain) и сбор SYN-cookie;
- разнесение RX-контекстов через IPv4-фрагментацию и проверка рабочих
  split-точек пути;
- обнаружение утечки RST локального ядра и временный OUTPUT-фильтр iptables;
- --spoof: захват свободного адреса на локальном сегменте через ARP;
- встроенный watcher живости цели (TARGET DOWN → код возврата 3);
- офлайн-проверки --selftest (работает на любой ОС, без root) и --dry-run.

Требования
----------

Атакующая машина:

- Linux с IPv4 raw sockets и AF_PACKET;
- root либо CAP_NET_RAW; для автоматического iptables-правила и SO_MARK
  дополнительно нужен CAP_NET_ADMIN;
- установленный iptables, если не используется --no-rst-filter или --spoof;
- сетевой маршрут до TCP-порта цели;
- прохождение IPv4-фрагментов без фильтрации и преждевременной сборки.

Цель:

- ядро Linux без исправления 4e2b3ef19e0e ("inet: reject unhashed sockets
  during established lookups");
- открытый TCP-listener (nginx, sshd, любой listen());
- net.ipv4.tcp_syncookies=1 для race (по умолчанию в Linux) либо 2 для tw;
- две или более RX-очереди на ingress-интерфейсе либо включённый RPS.

Проверить цель заранее:

    nstat -az | grep -E 'SyncookiesSent|SyncookiesRecv|EmbryonicRsts|ListenOverflows'
    ss -lnt
    ethtool -l eth0
    cat /sys/class/net/eth0/queues/rx-*/rps_cpus

Сборка и проверка
-----------------

    cargo build --release
    cargo test
    ./target/release/noisytcp --selftest
    ./target/release/noisytcp --dry-run

--selftest собирает все типы пакетов с фиксированными адресами, проверяет
контрольные суммы, поля заголовков и сборку фрагментов и печатает hexdump.
--dry-run строит полный раунд гонки без сокетов и без отправки пакетов.
Обе проверки не требуют root и сети; --selftest и cargo test работают на
любой ОС, сам движок — только на Linux.

Готовый бинарник: ./target/release/noisytcp

Быстрый старт
-------------

Одна команда для всех проверок, автоматической калибровки backlog/batch и
работы до Ctrl+C:

    sudo ./target/release/noisytcp 192.168.1.100 22

Явно заданные backlog и batch, работа 10 минут:

    sudo ./target/release/noisytcp 192.168.1.100 22 --backlog 128 --batch 128 --duration 600

Цель с tcp_syncookies=2 и listener'ом, который закрывает соединение сразу
после accept:

    sudo ./target/release/noisytcp 192.168.1.100 9000 --mode tw

Без iptables и без RST от локального ядра — захват свободного адреса на
сегменте цели:

    sudo ./target/release/noisytcp 192.168.1.100 22 --spoof --src 192.168.1.77

Остановка: Ctrl+C (SIGINT) или SIGTERM.

Режимы
------

--mode probe
    Диагностика пути: один обычный SYN и проверка SYN-ACK, проверка утечки
    RST локального ядра, затем проверка фрагментированного пути на split
    точках 8/24/32/40. Ничего не калибрует и не атакует.

--mode verify
    Пять шагов: проверка утечки RST, измерение RTT и SYN-ACK timeout,
    калибровка и насыщение SYN-очереди, сбор cookie, создание hashed
    request socket, проверка его наличия out-of-window SYN-пробой, затем
    RST + cookie ACK. Показывает, что полный cookie-цикл на цели работает.
    Строка "request socket is hashed" означает, что out-of-window SYN
    получил challenge ACK.

--mode race (по умолчанию)
    Сначала выполняет probe и verify, затем запускает гонку. При любой
    ошибке предполётной проверки программа печатает причину, завершается с
    кодом 1 и не переходит к следующему этапу.

--mode tw
    Для целей с tcp_syncookies=2, где SYN никогда не создаёт hashed
    request socket. Программа проводит кортеж через полное рукопожатие,
    закрывает его в TIME_WAIT и переиспользует сокет SYN'ом с ISN больше
    tw_rcv_nxt: tcp_timewait_state_process() возвращает TCP_TW_SYN, и
    tcp_conn_request() создаёт hashed request socket. Требуется listener,
    который принимает соединение и сразу его закрывает — например
    lab/close-listener.py.

Параметры
---------

Цель и режим:

--ip, PORT (позиционные)
    IPv4-адрес и TCP-порт цели. Порт по умолчанию 9000. Для --selftest и
    --dry-run адрес можно не указывать.

--mode probe|verify|race|tw
    Режим работы, по умолчанию race.

--duration S
    Остановить race/tw через S секунд; 0 — работать до Ctrl+C.

Очередь и кортежи:

--backlog N
    Пропустить калибровку и использовать заданный эффективный backlog
    (1..4096). Значение должно быть известно заранее.

--batch N
    Число кортежей в раунде, максимум 512. 0 — взять calibrated backlog,
    ограниченный 512.

--readers N
    Число фрагментированных lookup-пакетов на кортеж в выстреле, 1..16.
    Первый пакет — основной; остальные N-1 пар фрагментов отправляются
    сразу после второго фрагмента.

Окно гонки:

--frag-gap-us N
    Задержка между первым и вторым фрагментами lookup-пакета, мкс (20).

--free-gap-us N
    Задержка между завершением lookup и RST, освобождающим request socket (0).

--alloc-gap-us N
    Задержка между RST и cookie ACK, повторно выделяющим slab-слот (4).

--jitter-us N
    Случайная добавка к каждой задержке, мкс (4).

--settle-us N
    Ожидание обработки очереди между управляющими фазами, мкс (5000).
    Если verify не получает SYN-ACK после освобождения слота на медленной
    VM, увеличьте задержку.

--synack-ms N
    Таймаут SYN-ACK в миллисекундах. По умолчанию измеряется: 4*RTT+10,
    но не меньше 10 и не больше 2000.

Пакеты:

--payload N
    TCP-payload в фрагментированных lookup-пакетах, 0..256 (16). Должен
    быть достаточным, чтобы --frag-split поместился в сегмент.

--frag-split N
    Сколько TCP-байт несёт первый фрагмент; кратно 8 и меньше 20+payload.
    Если не задан, probe выбирает рабочую точку, предпочитая 24.

--mss N
    MSS, объявляемый в SYN; фиксирует MSS-индекс SYN-cookie (0 — не
    объявлять). Во время запуска значение должно быть постоянным.

Исходные порты и сеть:

--source-port N
    Первый исходный порт (40000).

--source-port-count N
    Число портов, доступных движку (16384, минимум 1024). Диапазон
    40000..56383 по умолчанию.

--src IP
    Адрес источника. Без --spoof должен быть локальным. С --spoof —
    нелокальным адресом на сегменте цели.

--spoof
    Захватить --src через ARP на локальном сегменте. Локальное ядро не
    владеет адресом и не отправляет RST, поэтому iptables не нужен.
    Требуется цель on-link (маршрут без шлюза) и --src.

--dev NAME
    Сетевой интерфейс для сниффера, ARP и отправки (SO_BINDTODEVICE). По
    умолчанию — из таблицы маршрутов.

--mark N
    Значение SO_MARK для своих пакетов (1). Используется фильтром RST.
    --mark 0 отключает SO_MARK (нужно, если нет CAP_NET_ADMIN).

Защита и наблюдение:

--no-rst-filter
    Не устанавливать временное правило iptables. Эквивалентное правило
    должно быть установлено заранее.

--assume-ok
    Продолжать, даже если обнаружены RST от локального ядра. Обычно делает
    гонку бесполезной.

--keep-children
    Не отправлять RST дочерним сокетам, созданным cookie ACK. Accept-очередь
    цели постепенно заполняется, и новые cookie-сокеты перестают
    создаваться; используйте только для наблюдения.

--pin
    Привязать движок, сниффер и watcher к разным CPU.

--no-watch
    Не запускать встроенный watcher живости цели в race/tw.

--debug
    Печатать диагностику калибровки, кадров и ошибок отправки.

Защита от локального RST
------------------------

Когда сервер отвечает SYN-ACK на исходный порт без локального TCP-сокета,
ядро атакующей машины отправляет RST с seq=ISN+1. Такой RST преждевременно
удаляет request socket на цели.

Программа помечает свои пакеты через SO_MARK и по умолчанию временно
добавляет правило:

    iptables -I OUTPUT -p tcp --sport 40000:56383 --tcp-flags RST RST \
        -m mark ! --mark 0x1 -j DROP

Правило удаляется при нормальном завершении и по Ctrl+C/SIGTERM. Если такое
правило уже существует, программа его не удаляет. Диапазон меняется через
--source-port и --source-port-count, mark — через --mark.

При --no-rst-filter программа проверяет утечку RST и останавливается с
командой для ручной настройки. --assume-ok разрешает продолжить, но обычно
делает гонку бесполезной.

С --spoof локальное ядро не владеет адресом источника, поэтому RST не
возникает: программа рассылает gratuitous ARP, отвечает на ARP-запросы цели
и не трогает iptables.

Как работает гонка
------------------

Один раунд (--batch кортежей):

1. Очистка предыдущих кортежей
   Контролируемые RST для request/harvest ISN предыдущего раунда и для всех
   filler-запросов.

2. Насыщение SYN-очереди
   Очередь заполняется calibrated_fill "мусорными" SYN с запоминанием
   порта и ISN каждого. Это переводит listener в режим SYN cookies.

3. Сбор cookie
   Для каждого кортежа отправляется SYN с отдельным client ISN; программа
   ждёт SYN-ACK, у которого acknowledgment = ISN+1, и сохраняет server ISN
   как cookie.

4. Создание request socket
   Очередь полностью очищается контролируемыми RST и заполняется заново
   ровно на batch запросов с новыми ISN: при свободной очереди сервер
   создаёт hashed request_sock R.

5. Lookup/free/reallocate
   Сначала отправляются первые фрагменты ACK с seq=request_ISN+1 и ack=0
   (заранее), затем через frag-gap — вторые фрагменты: сборка запускает
   lockless established lookup в другом RX-контексте. Далее для каждого
   кортежа: free-gap, обычный RST с seq=request_ISN+1 освобождает R,
   alloc-gap, обычный ACK с сохранённым cookie вызывает
   tcp_get_cookie_sock() и повторное выделение slab-слота. Последний RST
   очищает созданный child socket (если не задан --keep-children).

Задержки frag/free/alloc и случайный jitter подбирают фазу между двумя
RX-контекстами. Один раунд обрабатывает batch кортежей; после него
оставшиеся сокеты очищаются.

Режим TIME_WAIT
---------------

Для tcp_syncookies=2 обычный SYN всегда получает cookie и никогда не
создаёт hashed request socket. tw-режим использует другой путь:

1. SYN (ISN s1) → SYN-ACK с cookie; сохраняется cookie.
2. ACK с ack=cookie+1 завершает рукопожатие; listener принимает и сразу
   закрывает соединение (FIN).
3. ACK и FIN отправляются отдельными сегментами: совмещённый ACK+FIN
   попадает в "bad case" в tcp_fin() и откладывает TIME_WAIT.
4. Сервер уходит в TIME_WAIT.
5. SYN с ISN s2 = s1+3 (строго больше tw_rcv_nxt = s1+2) заставляет
   tcp_timewait_state_process() вернуть TCP_TW_SYN; tcp_conn_request()
   создаёт hashed request socket R.
6. Далее тот же выстрел free/realloc, что и в race.

Требуется listener, который закрывает соединение сразу после accept
(lab/close-listener.py). На каждом неудачном шаге кортеж аккуратно
разбирается RST, чтобы полуоткрытые сокеты не копились.

Watcher живости и коды возврата
-------------------------------

В race и tw по умолчанию работает watcher: раз в секунду обычный TCP
connect на порт цели (source-порт вне диапазона движка, в --spoof — с
локального адреса маршрута). При syncookies живая цель отвечает даже при
насыщенной SYN-очереди, поэтому четыре подряд неудачи за ~10 секунд означают
TARGET DOWN: программа печатает время, останавливается и завершается с
кодом 3. Отключить: --no-watch.

Коды возврата:

0   запуск завершён (в том числе по Ctrl+C), цель не объявлена упавшей;
1   ошибка выполнения или предполётной проверки;
2   некорректные аргументы командной строки;
3   watcher объявил цель недоступной (вероятный kernel panic).

Статистика
----------

Строка раз в 5 секунд и итоговая:

    [  12.3s] rounds=... attempts=... (N/s) cookies=... synacks=... packets=... timeouts=... send_errors=... rst_leaks=...

rounds      выполненные управляемые раунды;
attempts    попытки lookup/free/reallocate, для которых был получен cookie;
cookies     полученные подходящие SYN-ACK во время сбора cookie;
synacks     все подходящие SYN-ACK, замеченные сниффером (включая filler);
packets     успешно отправленные IPv4-пакеты, включая отдельные фрагменты;
timeouts    истёкшие ожидания SYN-ACK и probe-ответов;
send_errors ошибки raw socket при отправке;
rst_leaks   обнаруженные RST от локального ядра.

Рост packets или attempts не доказывает срабатывание уязвимости. Результат
нужно подтверждать через serial-консоль, kmsg или систему мониторинга цели.
Характерная паника содержит NULL dereference по адресу 0x12 в tcp_v4_rcv.

Диагностика
-----------

"no valid SYN-ACK from ... within 2 seconds"
    Listener не отвечает: проверьте порт, маршрут, firewall и что цель
    действительно слушает.

"the path drops or reassembles IPv4 fragments..."
    Путь не пропускает фрагменты. Разнесения RX-контекстов не будет;
    перейдите в L3-домен цели или обойдите собирающий фрагменты хоп.

"the configured --frag-split N is dropped by the path"
    Укажите рабочую точку из списка working splits или уберите --frag-split.

"working splits ... do not fit the ...-byte reader segment"
    Увеличьте --payload, чтобы выбранный split помещался в сегмент.

"the local kernel answered SYN-ACK with RST"
    Не работает фильтр RST. Установите правило из сообщения, проверьте
    --mark/--source-port или используйте --spoof.

"SYN queue did not saturate up to N"
    SYN cookies выключены, backlog больше 4096 либо очередь не успевает
    заполняться. Проверьте tcp_syncookies=1 и задайте --backlog вручную.

"the listener returns cookies immediately (tcp_syncookies=2)"
    Цель всегда отвечает cookie; используйте --mode tw.

"request socket is absent: the tuple took the cookie path again"
    На шаге создания request socket очередь была ещё полна. Увеличьте
    --settle-us или уменьшите --batch.

"no response to the request-socket challenge probe"
    Out-of-window SYN не получил ни challenge ACK, ни SYN-ACK: проверьте
    фильтры и фрагментацию.

"no cookies were harvested; no race attempt was possible"
    Ни один кортеж не получил cookie. Сначала добейтесь успешного
    --mode verify.

Если verify не видит hashed request, гонку запускать бессмысленно. Если
cookies не растут, проверьте backlog, syncookies, RTT и фильтрацию.

Ограничения
-----------

Это вероятностная гонка с окном в несколько наносекунд. По опубликованному
advisory, на QEMU/KVM с vCPU preemption срабатывание занимало от секунд до
минут, а на тихом bare-metal — около 14 часов даже с настроенным PoC.
Успех не гарантируется.

Нужны две или более RX-очереди либо RPS: иначе фрагментированный и обычный
пакет одного кортежа обрабатываются одним контекстом и окно не возникает.

Программа не подтверждает панику сама: watcher видит только потерю TCP.
Для точного подтверждения нужен serial-консоль или kmsg цели.

Отладочные хуки
---------------

Для отладки ядра цели под GDB предусмотрены переменные окружения (в обычной
работе не задавайте их):

NOISYTCP_GDB_READY=<path>
    После предполётных проверок race ждёт появления файла (до 60 с), затем
    удаляет его и начинает гонку.

NOISYTCP_GDB_TUPLE=<path>
    Перед отправкой первого фрагмента кортежа программа пишет в файл его
    source-порт и ждёт 50 мс, чтобы отладчик успел поставить breakpoint.

NOISYTCP_GDB_SYNC=<path>
    После второго фрагмента кортежа программа ждёт появления файла (до 5 с)
    и удаляет его — точка синхронизации с отладчиком.
