NoisyTCP (noisytcp) — инструкция
================================

Назначение
----------

noisytcp пытается вызвать request_sock Reuse ABA Race CVE-2026-99288 в TCP-стеке Linux и удалённый kernel panic. Это активный exploit-режим, а не сканер или проверка версии ядра.

Программа предназначена только для исследования собственных машин и изолированных лабораторных стендов. Запуск может полностью остановить целевой Linux-хост и все его контейнеры.

Реализован IPv4 request-queue-путь. Режимы IPv6, TIME_WAIT и full child socket ABA не реализованы.

Требования
----------

Атакующая машина:
- Linux с IPv4 raw sockets и AF_PACKET;
- root, либо CAP_NET_RAW и CAP_NET_ADMIN;
- iptables для автоматически устанавливаемого OUTPUT-фильтра;
- сетевой маршрут до TCP-порта цели;
- прохождение IPv4-фрагментов без фильтрации или преждевременной сборки.

Цель:
- ядро без исправления CVE-2026-99288;
- открытый TCP-listener;
- net.ipv4.tcp_syncookies=1 (режим syncookies=2 не поддерживается);
- две или более RX-очереди либо включённый RPS.

При ручном управлении RST-фильтром можно передать --no-rst-filter; тогда CAP_NET_ADMIN и iptables не требуются, но эквивалентное правило должно быть установлено заранее.

Сборка
------

cargo build --release

Готовый Linux-бинарник:

./target/release/noisytcp

Проверка перед атакой
---------------------

1. Проверить обычный и фрагментированный SYN/SYN-ACK и отсутствие RST от локального ядра:

sudo ./target/release/noisytcp 192.168.1.100 22 --mode probe

2. Проверить калибровку SYN-очереди, получение cookie и создание hashed request socket:

sudo ./target/release/noisytcp 192.168.1.100 22 --mode verify

На цели полезно одновременно наблюдать:

nstat -az | grep -E 'SyncookiesSent|SyncookiesRecv|EmbryonicRsts|ListenOverflows'

В verify должны увеличиваться SyncookiesRecv и EmbryonicRsts. Строка "request socket is hashed" означает, что out-of-window SYN получил challenge ACK.

Запуск гонки
------------

Режим race по умолчанию выполняет probe, затем verify и только после их успеха запускает гонку. При любой ошибке программа выводит причину, завершается с кодом 1 и не переходит к следующему этапу. Отдельные --mode probe и --mode verify нужны только для ручной диагностики.

Одна команда для всех проверок, автоматической калибровки backlog/batch и работы до Ctrl+C:

sudo ./target/release/noisytcp 192.168.1.100 22

Явно заданные backlog и batch, работа 10 минут:

sudo ./target/release/noisytcp 192.168.1.100 22 --backlog 128 --batch 128 --duration 600

Настройка окна гонки:

sudo ./target/release/noisytcp 192.168.1.100 22 \
    --frag-gap-us 20 --free-gap-us 0 --alloc-gap-us 4 --jitter-us 4 --readers 2

Если RTT измерен неверно или ответы приходят поздно:

sudo ./target/release/noisytcp 192.168.1.100 22 --synack-ms 200

Остановка:

Ctrl+C

Защита от локального RST
------------------------

Когда сервер отвечает SYN-ACK на исходный порт без локального TCP-сокета, ядро атакующей машины отправляет RST с seq=ISN+1. Такой RST преждевременно удаляет request socket на цели.

Программа помечает свои пакеты через SO_MARK и по умолчанию временно добавляет правило:

iptables -I OUTPUT -p tcp --sport 40000:56383 --tcp-flags RST RST \
    -m mark ! --mark 0x1 -j DROP

Правило удаляется при нормальном завершении и по Ctrl+C/SIGTERM. Если такое правило уже существует, программа его не удаляет. Диапазон меняется через --source-port и --source-port-count, mark — через --mark.

При --no-rst-filter программа проверяет утечку RST и останавливается с командой для ручной настройки. --assume-ok разрешает продолжить, но обычно делает гонку бесполезной.

Что делает программа
--------------------

1. AF_PACKET receiver
   Отдельный поток получает ответы цели и наблюдает исходящие RST локального ядра. Для SYN-ACK проверяются адреса, порты и acknowledgment=client_ISN+1, поэтому старый ответ не принимается за текущий.

2. RTT probe и калибровка
   Программа измеряет RTT и подбирает SYN-ACK timeout. Бинарный поиск определяет минимальное число half-open запросов, при котором listener начинает отвечать через SYN cookies.

3. Cookie harvest
   SYN-очередь полностью очищается контролируемыми RST и заполняется точным числом запросов. Для каждого race-кортежа отправляется SYN с отдельным client ISN и сохраняется полученный cookie.

4. Создание request socket
   SYN-очередь снова полностью очищается. Для тех же кортежей отправляются SYN с новыми ISN; теперь сервер создаёт hashed request_sock R.

5. Lookup/free/reallocate race
   Первый IPv4-фрагмент ACK с seq=request_ISN+1 и ack=0 отправляется заранее. Второй фрагмент запускает reassembly и lockless established lookup в другом RX-контексте. Затем обычный RST с seq=request_ISN+1 освобождает R, а обычный ACK с сохранённым cookie вызывает tcp_get_cookie_sock() и повторное выделение slab-слота. Последний RST очищает созданный child socket.

Задержки frag/free/alloc и случайный jitter подбирают фазу между двумя RX-контекстами. Один раунд обрабатывает batch кортежей; после него оставшиеся сокеты очищаются.

Основные параметры
------------------

--mode probe|verify|race
    Диагностика, проверка полного cookie-цикла или непрерывная гонка.

--backlog N
    Пропустить калибровку и использовать заданный эффективный backlog.

--batch N
    Число кортежей в раунде, максимум 512. Значение 0 выбирает calibrated backlog, ограниченный 512.

--readers N
    Число фрагментированных lookup-пакетов на попытку, 1..16.

--duration S
    Остановить race через S секунд. 0 — работать до Ctrl+C.

--frag-gap-us / --free-gap-us / --alloc-gap-us
    Задержки между вторым фрагментом, RST и cookie ACK.

--jitter-us N
    Случайная добавка к каждой задержке для перебора фазы.

--settle-us N
    Ожидание обработки очереди между управляющими фазами, по умолчанию 5000 мкс. Если verify не получает SYN-ACK после освобождения слота на медленной VM, увеличьте задержку.

--source-port / --source-port-count
    Диапазон исходных портов. По умолчанию 40000..56383.

--debug
    Диагностика калибровки, кадров и ошибок отправки.

Статистика
----------

rounds
    Выполненные управляемые раунды.

attempts
    Попытки lookup/free/reallocate, для которых был получен cookie.

cookies
    Полученные подходящие SYN-ACK во время cookie harvest.

synacks
    Все подходящие SYN-ACK, замеченные AF_PACKET receiver.

packets
    Успешно отправленные IPv4-пакеты, включая отдельные фрагменты.

timeouts
    Истёкшие ожидания SYN-ACK и probe-ответов.

send_errors
    Ошибки raw socket при отправке.

Рост packets или attempts не доказывает срабатывание уязвимости. Результат нужно подтверждать через serial-консоль, kmsg или систему мониторинга цели. Характерная паника содержит NULL dereference по адресу 0x12 в tcp_v4_rcv.

Ограничения
-----------

Это вероятностная гонка с окном в несколько наносекунд. По опубликованному advisory, на QEMU/KVM с vCPU preemption срабатывание занимало от секунд до минут, а на тихом bare-metal — около 14 часов даже с настроенным PoC. Успех не гарантируется.

Если cookies не растут, проверьте backlog, syncookies, RTT и фильтрацию. Если verify не видит hashed request, гонку запускать бессмысленно. Если путь отбрасывает или собирает фрагменты, разнесение RX-контекстов не произойдёт.
